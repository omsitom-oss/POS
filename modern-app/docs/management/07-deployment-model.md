# Deployment model

`Deployments` records how a customer installation is configured; it is separate from `Customers`. A customer can change deployment over time without changing `CustomerId`.

Allowed combinations are enforced by a CHECK constraint:

| DeploymentType | HostingMode |
|---|---|
| `LOCAL_SQLITE` | NULL |
| `LOCAL_SQLSERVER` | NULL |
| `ONLINE` | `SHARED` or `DEDICATED` |

Deployment statuses are `PLANNED`, `ACTIVE`, `INACTIVE` and `DECOMMISSIONED`. The table stores no database password or full connection string. A local SQL Server deployment belongs to a customer's network and is not represented as an online `DatabaseServer`.

`Installations` belongs to both a customer and that customer's deployment. A composite FK prevents attaching an installation to another customer's deployment. `PublicId` is unique; `(CustomerId, DeviceIdentifier)` prevents accidental duplicate registration within one customer's installations. The device identifier is generated by the application; invasive hardware fingerprinting is not used. Status values are `ACTIVE`, `DISABLED`, `RETIRED`.

`DatabaseAssignments` is only for online deployments. It references an online deployment with the same customer and hosting mode, plus a managed `DatabaseServer`. The duplicated constrained `DeploymentType` column is `ONLINE` so the composite FK and CHECK can enforce online-only assignment at the database level. Shared assignments can use the same server/database name for multiple customers. Active dedicated assignments cannot share a server/database name.

Automatic provisioning, local POS schemas, license/deployment screens and configuration workflows are not implemented yet.
