# Elite POS replacement application rules

This directory contains the new application. The legacy VB.NET application and legacy SQL Server database are read-only references.

## Permanent rules

- Do not modify the legacy application or legacy database.
- Do not migrate a real business form unless the user explicitly asks.
- Keep the system small: no microservices, queues, event buses, CQRS, speculative repositories, or layers without a concrete need.
- React and TypeScript are the UI. React must never connect directly to SQL Server or SQLite. All database access goes through the local .NET service.
- Keep business screens as ordinary React components. They must not depend on a desktop shell API.
- Keep reusable visual behavior in `frontend/src/components` and tokens in `frontend/src/styles`. Feature pages compose shared components and do not introduce their own global styles.
- Every new screen must use shared semantic design tokens and components. Do not introduce page-specific typography, spacing, colors, tables, controls, or dialog visual systems.
- Elite POS has exactly Light and Dark modes. One direct header button toggles them; Light is the default and the choice persists locally. There is no System mode or theme menu.
- English is LTR and Arabic is RTL. Normal screens display only the active language; bilingual fields are shown together only when maintaining translated master data. Use logical CSS properties and verify shell, dialogs, tables, cards, and navigation in both directions.
- Bilingual master-data administration tables may show Arabic and English columns together when that helps maintain translations; ordinary POS business screens continue to show only the active language. Keep cell direction appropriate to each language.
- Header language switching is one compact EN/AR action that switches directly to the other language; no dropdown or popup.
- The Settings home uses compact SettingType cards; flat settings use a table and hierarchical settings use card drill-down with URL-backed breadcrumbs, never a tree UI.
- Keep normal UI text comfortably readable: body and table text should generally be 14-16px, labels 14-15px, and helper text at least 13px. Arabic needs comfortable line height.
- The shared UI font is `Simplified Arabic` with the centralized fallback stack in `frontend/src/styles/system.css`; do not introduce page-specific font families.
- Simple master-data Add/Edit flows use centered modal dialogs. System-generated Setting Code and SortOrder are not user-editable and are excluded from write DTOs. Setting icons are not stored in the database; UI icons are monochrome and theme-following.
- SettingType administration follows the same rule: users edit only localized names and supported flags. New type Code and SortOrder are generated by the backend; existing system type codes remain stable. Type deactivation is confirmed and never cascades to Settings.
- Use the shared Button variants (`primary`, `secondary`, `outline`, `ghost`, `danger`, `icon`) and semantic theme tokens. Do not override all buttons with a generic theme surface background; each variant owns its theme background, foreground, border, hover, focus, and disabled states.
- Use CSS logical properties (`inline-start`, `inline-end`, `block-start`, `block-end`) and test both RTL and LTR.
- Keep SQL parameterized. Never put credentials or secrets in frontend code or committed configuration. Customer/local POS SQL Server connections use Windows Integrated Security; SQLite uses a local file.
- The central `POSManagement` database is separate from customer POS databases. Only the .NET backend may connect to it, through `ConnectionStrings:POSManagement` supplied by .NET User Secrets or environment configuration. Never expose its credentials through React, APIs, logs, or documentation.
- Configuration first is permanent: customer names/IDs, business types, deployment or hosting modes, server addresses, database names, and customer-specific connection details are Management data. Normal onboarding or deployment must not require source-code changes or customer-specific conditions.
- Keep Management schema changes in the versioned `Data/Management/Migrations` stream. Future customer POS schema migrations must use a separate stream and must never be applied to `POSManagement`.
- Customer POS SQL Server connections come from the single backend configuration key `ConnectionStrings:POS`; local development uses `appsettings.Development.json` with Windows Integrated Security. Never scatter connection strings through services or expose them to React.
- Keep customer POS migrations under `Data/Pos/Migrations`, separate from `Data/Management/Migrations`. The explicit `--migrate-pos` command must verify the configured database identity and refuse unexpected objects before writing.
- The generic POS reference-data model is only `SettingTypes` plus `Settings`. Use it for simple localized name/code/hierarchy values; do not use it for entities with meaningful business data, specialized rules, financial/security behavior, or transaction history. Deactivate referenced settings instead of physically deleting them.
- Setting types are selected by stable codes, never hard-coded numeric IDs. Hierarchy validation belongs in the backend as well as applicable SQL constraints; preserve Arabic and English values on each setting row.
- `POSManagement` stores customer registration and control-plane records only. Items, sales, purchases, inventory, accounting, and other POS operations belong in customer POS databases.
- For future shared online databases, tenant ownership must come from authenticated server-side context. Operational rows and uniqueness/index rules must be scoped by `CustomerId` where appropriate. Never treat a client-supplied `CustomerId` as authorization.
- Add destination schema changes only as small, versioned migrations when a real workflow needs them. Do not reproduce the legacy schema speculatively.
- Design Lab data is fake and must remain independent of the legacy database.

## Architecture

`frontend` is a normal Vite React app, hosted in a browser during development. `server` is one .NET local service. The service owns the active provider and creates database connections. Provider choice comes from .NET configuration (`Database:Provider`); SQL Server and SQLite may use provider-specific SQL where needed. A desktop wrapper is not part of the current foundation. If Windows packaging is later requested, keep it a thin WebView2 host around the same web UI and local service.

## Project map

- `frontend/src/app`: app entry, locale, navigation state.
- `frontend/src/components`: shared inputs, buttons, dialogs, tabs, status and DataTable.
- `frontend/src/features/design-lab`: fake-data component demonstrations only.
- `frontend/src/layouts`: shared shell, sidebar, top bar, page header and toolbar.
- `frontend/src/styles`: global tokens, reset, direction-aware styles.
- `docs/ui`: shared design system, theme, sizing, table, form, dialog, and direction rules.
- `server/Data`: local POS provider options, connection factory and schema version table.
- `server/Data/Management`: dedicated Management SQL Server connection, migration runner and `Migrations` scripts for `POSManagement`.
- `server/Endpoints`: minimal API route groups.
- `server/Models`: small configuration/status models.
- `server/Services`: database health and first Management customer operations.
- `frontend/src/features/management`: customer list, create form and details, composed from shared design-system components.
- `frontend/src/features/settings`: generic reference-data administration using compact type cards, a shared flat table, and route-backed card drill-down for hierarchies.
- `frontend/src/components/SettingSelect.tsx`: reusable setting-type-code selector. Settings hierarchy is presented as card drill-down, not a tree.
- `server/Data/Pos`: customer POS migrations and settings persistence, isolated from Management.
- `docs/pos/settings`: legacy lookup mapping, schema, API, UI, and migration boundaries.
- `docs/management`: Management schema, identity, deployment, hosting and security decisions.

## Run locally

Start the service in one terminal:

```powershell
cd server
dotnet run
```

It listens on `http://127.0.0.1:5080`. The base configuration defaults to `server/data/elite-pos.db`; the Development profile selects `ConnectionStrings:POS` and SQL Server. Normal startup does not apply customer POS business migrations.

Start the React UI in a second terminal:

```powershell
cd frontend
npm install
npm run dev
```

Open the URL printed by Vite (normally `http://localhost:5173`). Vite proxies `/api` requests to the local service.

The Development profile selects the local SQL Server database `POS` through `ConnectionStrings:POS` (Windows Integrated Security). Apply its versioned settings schema explicitly:

```powershell
cd server
dotnet run -- --migrate-pos
dotnet run
```

The migration verifies that the active database is named `POS` and refuses unknown user objects. Normal startup does not apply customer POS migrations. Never point it at the legacy database or `POSManagement`.

For local Management development, configure `ConnectionStrings:POSManagement` using .NET User Secrets from the `server` directory. Apply its dedicated, transactional migration explicitly with `dotnet run -- --migrate-management`; normal server startup never applies Management schema changes. See `docs/management/04-management-migrations.md`. Do not put the Management connection string in appsettings, React configuration, or committed files.
